# img2cli 当前问题基线 (2026-08-09)

> 本文档是 img2cli 当前问题的**基线**。平台/环境层面的已知限制见根目录 [`KNOWN_ISSUES.md`](../KNOWN_ISSUES.md)。
> **写作原则:严格区分"实测现象"与"已证明根因"。** 能复现的现象写死;内部机制只作工作假设,不预先定论。

---

## 0. 一句话定位

> **v0.3.10 的主要限制不是截图或上传,而是 GUI 输入注入无法可靠确认目标应用是否真正接收了文本;不同宿主对合成输入的兼容性差异很大,因此 img2cli 需要从"单一全局注入模式"演进为"按宿主选择输入策略,并始终提供可靠的 Copy fallback"。**

链路拆解:截图 → 上传 → 注入。**截图和上传已通** (远程文件确实到位,见 `/tmp/img2cli/img_*.jpg`)。瓶颈在第三段:把路径送进目标窗口。

---

## 1. 核心问题:输入注入无法确认送达 (宿主兼容性差异)

### 1.1 现象 (实测,可复现)

img2cli 把远程路径"打"进目标窗口,靠模拟键盘:

| 模式 | 底层实现 |
|---|---|
| `Auto` / `Swap` / `PasteKeep` | Win32 `SendInput` 虚拟键 `Ctrl+V` |
| `Direct` | Enigo Unicode 字符输入 (底层 `SendInput` + `KEYEVENTF_UNICODE`) |
| `Copy` | 只写剪贴板,不模拟键盘 |

不同宿主对合成输入的接受程度差异极大:

| 宿主 | 虚拟键 Ctrl+V (Auto/Swap/PasteKeep) | Enigo Unicode (Direct) |
|---|---|---|
| 普通终端 (Windows Terminal / cmd / 本机直跑的 Claude Code) | ✅ | ✅¹ |
| **VSCode 集成终端** | ❌ (`SendInput` 返回 `inserted=0`) | ✅ **管理员下能成** |
| **Orca agent terminal** (onorca.dev) | ❌ | ❌ **管理员下也无效** |
| 网页版 (Chrome 标签里的 AI) | ❌ | 未实测 |

¹ Direct 受 UIPI 约束:img2cli 完整性须 ≥ 目标窗口。同权限直接可用;注入提权窗口才需 img2cli 自身提权。

### 1.2 关于根因 (工作假设,尚未证明)

⚠️ 以下是**工作假设,不是已证根因**,仅用于指导方向:

- 常见解释之一是"Chromium/Electron 检测并丢弃带 `LLKHF_INJECTED` 标志的合成事件"。但有两处对不上,说明这个解释不能照搬:
  1. VSCode 里 `SendInput` 返回 `inserted=0`,更像 **Windows 层面事件没插入成功**,而不是"插入成功后被下游过滤"(后者通常表现为"插入成功但目标无反应")。
  2. **VSCode 的 Direct (Enigo Unicode) 能成功** —— 若 Electron 一刀切拒绝所有 synthetic input,Direct 也该失败。它没失败,说明拒绝不是均匀的。
- 因此目前**只能确定**:不同宿主对合成输入兼容性差异极大,且 img2cli 注入后**无法确认目标是否真正消费了文本**。每个宿主内部按什么规则过滤,需要逐个验证,不该预先写死。

## 2. 最关键的缺陷:Direct 缺少可验证的 delivery acknowledgement

当前最该优先修的点。

**已证实的链路** (Orca 实测):

```text
Enigo text() 返回 Ok
  → img2cli 判断 Completed
  → Orca 没有收到可见输入
  → inject_with_fallback 的复制降级没触发
  → 剪贴板空 + 目标空:两边落空,零反馈
```

**已确定的根因**: `Ok` 只能证明**本地输入 API 调用成功**,不能证明**目标控件真正消费了文本**。Direct 模式没有任何 delivery acknowledgement。

**未确定的部分**: Orca 内部到底按什么规则过滤输入 (INJECTED 标志? `isTrusted`? 别的?),暂未证明 —— 也**不需要先证明**,上面的链路已经足够支撑架构改动。

**为什么是最糟的失败模式**: Auto/Swap 失败时 `SendInput` 返回 `<4` 会触发降级,至少把路径复制到剪贴板 (`ReadyToPaste`)。但 Direct 的 Enigo 永远返回 `Ok`,降级永远不触发 → 用户两边落空、零报错。

## 3. 默认配置与主用例不匹配

| 配置项 | 当前默认 | 问题 | 应该是 |
|---|---|---|---|
| `InjectionMode` | `Auto` | Chromium 宿主下 Auto 多数失败 → 强制走降级 | 按宿主选 (见 §4 P1) |
| `Wrap Single Quotes` | `ON` | Claude Code 认**裸路径**才 → `[Image #N]`;带单引号 `'...'` 不被识别为图片 | `OFF` (Claude Code profile 必关,已实测) |

---

## 4. 管理员依赖

Direct 模式绕 UIPI 通常要**以管理员运行** img2cli (托盘 "Restart as Administrator")。UX 差 (每次启动手动提权,且扩大安全面)。但 Direct 是 VSCode 类宿主唯一能自动工作的模式,暂时绕不开。

---

## 5. 后续主线 (优先级)

### P0 — 修 Direct 静默失败
Direct 即使返回 `Ok`,也**不能默认认为"目标已收到"**。两条路:
- 对已知不可靠宿主 (Orca 等) **直接走 Copy**;
- 或至少**始终保留一份引用在剪贴板** (哪怕 Direct 看似成功也写一份),保证用户有 Ctrl+V 兜底。

本质:把"注入成功"的定义从"API 返回 `Ok`"改成"**有可验证的送达确认**";在拿到确认前,Copy fallback 是默认保险。

### P1 — per-target policy
不再用一个全局 Injection Mode 管所有宿主。按前台窗口标题/类名自动判定:
- VSCode → Direct (+ 管理员)
- Orca → Copy (+ 提示手动 Ctrl+V)
- 普通终端 → Auto/Swap

### P2 — wrap_single_quotes 默认关掉 (AI CLI 主路径)
至少 Claude Code profile 用裸路径 (实测:裸路径 → `[Image #N]`,带引号不识别)。

### P3 — KNOWN_ISSUES.md 改为"实测矩阵 + 推荐策略"
从"解释根因"改成"记录可复现实测矩阵 + 推荐策略",避免 Windows/VSCode 更新后文档再次失真。现有 §2.C 已过时 (见 §6)。

### 更长期 — 程序化注入 (彻底绕开键盘栈)
唯一能根治"无法确认送达"的方向,但实现方式必须正确:

- **VSCode**: Companion Extension 调 `Terminal.sendText()` (官方 API,可靠)。
- **tmux/screen**: 用其正式 `send-keys` 接口 (img2cli 持有或能触达该 session)。
- **自管理**: img2cli 从一开始就持有 PTY master / 作为子进程父进程。
- **Orca**: 待调研是否有 CLI / 扩展 API / 主进程 IPC;Electron 理论上还能走 `--remote-debugging-port` 的 CDP。

⚠️ **不能**靠"打开 PTY slave `/dev/pts/N` 直接 `write()`" —— 那通常只是往终端回显字符,目标 CLI 不会把它当 stdin 输入,容易做成"终端显示了但应用没收到"。
